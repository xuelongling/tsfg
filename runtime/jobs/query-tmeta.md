# Query metadata and borrowed batch binding

`jobs.query_tmeta.Document.load` owns the development Query `.tmeta` data section. Its expected payload hash, input identity and package identity come from the independent producer cold reader. An `llvmArtifact` receipt from the paired producer binds the LLVM byte hash to those checked batch and metadata hashes. Receipts without a pair still support metadata and Store binding for data inspection. The hashes identify data and carry no executable authority.

The reader checks the canonical versioned envelope, complete payload hashes, target, component layout, ordered entries and standard function argument types. The complete original Source request/facts, checked batch and effects report remain in the owned document. Source/Core semantics are checked at the producer cold boundary; the Runtime does not implement another Source checker.

Query component layouts retain the existing layout envelope. Their `hirDigest` binds the complete `{components,target,types}` catalog and newline. This has a separate owning load entry from the existing Common HIR expected-identity path, whose contract is unchanged. A Store copies the validated layout payload identity along with its component directory.

`Document.bind(allocator, store, batch, entry_index, scalars)` checks the actual Store owner, layout identity, live session, row count, complete unique column selection, strides, alignment, access and buffer lengths. It creates an owned plan of row-count, column, stride and f32 scalar arguments. Repeated tuple occurrences select the same original column; a read occurrence returns a const slice even when a write occurrence shares that backing. Component data is never copied.

The plan owns its metadata and scalar values, so the document can be released after binding. The Store must outlive the plan and its Query/Batch, as required by the existing Store owner contract. Releasing either Query or Batch invalidates the complete session. Later argument and column access fails the existing token check. Tokens do not recover when another session is opened within that Store lifetime. Calling a plan after destroying its Store violates the owner lifetime contract.

`Plan.verifyCodeIdentity` compares a code owner's metadata and batch digests, selected entry symbol, logical function and signature identities, and exact argument ABI with the values retained by the plan. The check remains available after the document is released. The code owner supplies the independent identities and its executable lease.

`Plan.withCheckedBatch` verifies those identities and hashes the supplied raw LLVM bytes against the independently paired receipt before reserving the batch. The existing 8 MiB LLVM text limit applies. Missing or mismatched pairing returns `IdentityMismatch`. A release through any alias and a second active call on the same batch return `BorrowConflict`. Distinct batches in the query can be active simultaneously. Return and error both free the active-call reservation so the query can be released. The caller retains the plan and code version, and coordinates accesses through any other batch or plan aliases. The callback uses borrowed views only for the duration of the call.

`ParallelGroup.withCheckedPlans` checks the paired LLVM bytes and one code identity per selected loop before acquiring Store queries, including loops with zero rows. It pins every batch for the synchronous callback and delivers the plans in system order, then Store batch order. Return and error both release the pins and query leases. Both stage entry points borrow the immutable effects and entry metadata from the live Document through the callback. Batches of each selected loop share one column and tuple mapping and one snapshot of the evaluated scalar arguments.

`Plan.llvmArgument` supplies the emitted LLVM entry arguments in order. The row count comes first. Each unique column supplies allocated and aligned pointers, byte offset, byte length, byte stride of one, then the component's row stride. Scalar arguments follow with their original floating-point widths. The two pointers name the same aligned Store allocation and retain the column's read or write access. Inspection requires a live query and coordination with release. A caller invoking code uses the pointers inside `withCheckedBatch`, `withCheckedBatches` or `withCheckedPlans`.

Plans contain no executable address. They do not access FunctionCell, a loader, State, Guest or a scheduler, and do not claim CPU execution or entry publication. The entry symbol and logical function/signature identities remain in the explicit development candidate domain.

`Document.effects` owns the typed existing v3 report within the document arena. It retains every system, original loop, capability, ordered operation, helper call, source anchor and field count. A bounded projection of the already-owned Source declaration/type/loop directory checks identities and membership. The Runtime does not interpret Source expressions or resolve aliases again.

`effects.system(logical_id)` exposes the immutable system data. `effects.conflictComponents(left, right)` accepts distinct known logical system identities and returns the complete component-column conflict set in either query order. Unknown systems and self pairs are errors. The canonical pair order in serialized data gives no scheduling direction. Read/Read shares a column; a Write occurrence wins capability normalization, and access to different fields still conflicts when either system can write that component. A system's declared Query capabilities remain present even when it has no loop or memory operation.

The typed graph lives until `Document.deinit`; no allocator pointing to a local arena is retained. A bound plan's independent copied metadata does not extend the document graph lifetime. Later Jobs code consumes this checked data graph; this reader neither dispatches work nor grants callable or execution authority.
