# R02b：TypeScript 前端产品化

状态：2026-09-20 用户已确认 Q1–Q6 及最终共享理解，首批设计澄清已收口，可进入 to-spec。本文只记录已确认决定，不表示产品前端已实现或授权本轮实施。

## 权威、起点与范围

以[架构](tsfg-architecture.md)、[Roadmap R02b](tsfg-roadmap.md#r02btypescript-前端产品化)、[R01 语言契约](r01-language-contract.md)及 [R02a Source Intake](r02a-source-intake.md)的适用约束为准。默认复用固定官方 TypeScript 7.0.2 规则及前端，只在特殊且必要处客制化，不全量自建 parser、checker 或重新规定一般 TS 行为。

当前已经有可维护的官方 Go 前端消费探针与首个 TypeScript intake 完成记录；现有探针限单个源码文件及固定声明库，输出观测数据，不是 FrontendSnapshot 或完整产品模块图。上游具有项目快照、模块解析和增量相关源码，但本产品尚未接入这些能力，不能以其存在直接宣称产品能力通过。

R02b 提供源码输入、前端事实及诊断 interface。HIR/Core IR 与语义归一化归 R03，完整 Language Service 归 R12，完整编译/运行与 MLIR 链路不塞进本阶段。复用 R02a 既有来源、构建及验证入口；新增真实消费继续维护来源与许可闭包。

## Q1：独立拥有的 FrontendSnapshot — accepted

FrontendSnapshot 是独立拥有、不可变的产品数据，提供当前消费者需要的源码结构、符号、类型和诊断事实。上游会话关闭后仍可消费，不暴露上游 Program、AST、Checker、缓存或有效期约束。

仅投影真实消费者需要的事实，不完整复制 TypeScript AST，不把前端快照变成 HIR、SSA 或第二套语言语义。内部复用缓存或共享存储不得破坏外部不可变与独立拥有的含义；本 R02b 决定未锁定具体传输形式或编译器宿主语言。后续 R03 Q4 已于 2026-09-30 选择 C++/MLIR 中端，完整类型及泛型实例化事实投影须作为真实消费者依赖补齐，继续复用官方 checker 而不另造一般 TS 类型计算。所有权取舍见 [ADR-0014](adr/0014-owned-frontend-snapshot.md)，中端取舍见 [ADR-0015](adr/0015-mlir-backed-core-ir.md)。

## Q2：明确输入与官方解析 — accepted

调用方明确源码根、声明输入和前端配置，前端消费可追溯的输入集合。依赖可以由官方解析器在声明范围和配置内自动发现后固化，不要求用户手工枚举每个文件；不得悄悄消费集合之外的文件、隐式 JS 实现或宿主环境配置。

输入控制不另造模块语义。官方模块判定和解析规则继续沿用；具体模块配置与能力覆盖在实际消费者阶段确定，合法但尚未接入的形式记录待实现，不永久禁止。源码及声明的身份与内容须匹配，不能使文件入口和内存输入产生两套语言含义。

## Q3：先完成 cold compile 闭环 — accepted

首个交付按 R01 已定的单模块、顶层函数、i32/bool、局部变量、控制流与调用切片，先以 cold compile 建立真实前端正反例及 Snapshot 消费验收。前端成功不等于该程序已通过 lowering 或执行验收；已有 R01 runtime/trap oracle 不要求在前端阶段创建解释器来执行。

增量保留为 R02b 后续切片，接入时同步交付输入失效规则和与 cold compile 等价的证据。不先建设常驻服务、完整 LSP 或只有名称的增量 interface；R02b 的最终增量/模块责任不因此删除。额外标量、标记、值类型、引用与领域能力随相应已定语义切片补齐，不以首批子集宣布整个 R02b 完成。

## Q4：标识限定于所属 Snapshot — accepted

节点、符号和类型标识仅在所属 FrontendSnapshot 内有效；消费引用须关联所属 Snapshot 身份，不允许把另一份快照的标识当作当前对象。相同明确输入及前端契约下，结果须可确定复现，不使用进程地址、遍历偶然顺序或宿主绝对路径充当产品身份。

暂不承诺源码编辑后编号保持不变，也不把前端局部标识与 R04 的持久 FunctionId/TypeId 混用。具体身份组成、编号和摘要算法在 spec 中围绕真实 producer/consumer 固化，不为首批开发建立跨版本持久身份体系。

## Q5：错误分析不交付可 lowering 的成功 Snapshot — accepted

首批分析失败时返回结构化诊断及可取得的输入身份，不交付可供 lowering 使用的成功 FrontendSnapshot。可以复用官方错误恢复以收集诊断，但恢复生成的内部节点、错误类型或缺失事实不能伪装成已验证的产品事实。

此限制不禁止未来编辑器提供有明确部分/错误状态的分析结果；该能力随实际 Language Service 消费者交付，不作为首批前置。诊断错误、能力待实现、输入/工具失败分别如实报告，不通过制造语法错误来拒绝合法但尚未支持的 TS 结构。

## Q6：显式最小声明环境 — accepted

首批采用显式、版本化的最小 tsfg 声明环境，包含 i32/bool 必需声明与经审查的必要上游基础类型；不自动注入 DOM、Node 或完整 JS 运行时全局声明。用户声明也必须属于明确输入集合，声明身份和内容随分析输入记录。

声明须配合真实类型语义。仅把 i32 定义成 number 的普通别名无法满足 i32 与 f64 区分、精确整数字面量及禁止隐式数值转换等已定规则；这些必要差异应在复用官方分析的基础上适配，不能整体忽略上游诊断或另建一般 TS checker。

.d.ts 不构成 JS 实现，也不证明声明的外部函数已存在或可执行。后续原生接口、包与运行时消费者必须提供对应实现/绑定证据；首批不因有声明就声称具备这些能力，不为此重开 R01 语言设计。

## 继承的诊断与阶段约束

沿用 R01 的稳定 Diagnostic Code、规则关联、UTF-16 code-unit 半开区间及排序规则；上游诊断号、内部位置和类型打印文案不是产品机器契约。只支持既定 TS/声明/tsfg 制品输入边界，禁止 JS 输入、emit 和运行时回退；新增入口必须补相应正反例，不直接推广 R02a 单文件探针的证明。

本机开发沿用已确认的显式开发模式、来源/输入/工具可追溯及 E 盘落点；已有开发验收不冒充强隔离或发布认证。实际注册产品契约时须核查并迁移来源探针对空 Contract Registry 的旧假设，保持 R02a 回归；不为此新开语言或仓库设计决定。

## 首批验收与后续交接

首批闭环为明确 TS/声明输入 → 官方前端与必要 tsfg 语义适配 → 独立 FrontendSnapshot 或结构化诊断 → 仅依赖产品 interface 的真实消费验证。该消费验证须读取实际源码结构、引用/类型事实并验证其关联及会话关闭后的有效性，不能只比较空对象、类型打印字符串或版本号；不要求实现 R03 lowering 来验证 interface。

验收覆盖首批 R01 语义适用的正反例、未支持与禁止项拒绝、Snapshot 混用拒绝、确定性结果、错误不产生成功快照，以及新增入口的 JS 隔离。复用上游位置转换并补非 ASCII、CRLF 等案例，验证 R01 UTF-16 源码位置；运行时结果与 trap 仍留给执行消费者，不能把前端验收冒充执行通过。

当前 Q1–Q6 已确定首批设计，没有待答的普通 TS 规则问题。具体字段、投影布局、编号/摘要算法、诊断映射、源码适配落点和既有构建契约迁移由后续 spec/实施依据事实明确；不以未选择可替换实现细节为由继续无界访谈。若发现无法满足既定承诺的真实冲突，再提出最小设计决定。

多模块、增量、完整类型族和领域语义仍按 R02b 的后续能力切片交付，完整 Language Service 归 R12；本次首批收口不等于整个 R02b 完成。用户已确认最终共享理解，下一步可按请求进入 to-spec，再经 to-tickets 审批拆票，实施另行授权。本轮未创建 spec/tickets、修改实现或执行构建。
