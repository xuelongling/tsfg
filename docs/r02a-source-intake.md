# R02a：上游源码治理与可复现集成

状态：Q1–Q9 及最终共享理解已于 2026-09-10 获用户确认，grill 已收口。本文记录已批准边界，不表示源码准入、构建或执行验收已经完成。

## 1. 范围与事实来源

本规范属于 [Roadmap R02a](tsfg-roadmap.md#r02a上游源码治理与可复现集成)，以 [架构](tsfg-architecture.md)、[工程章程](r00-engineering-charter.md)、[R01 语言契约](r01-language-contract.md)及有效 ECP/ADR 为准。历史候选表不是全部来源的准入许可。

TypeScript 来源先供 W1 前端消费；2026-09-30 R03 Q4 已确认以 MLIR 基础设施承载 Core IR，因此 MLIR/LLVM 须在 R03 实际使用前完成对应 intake，而非等到 W2 AOT 才启动准入。具体源码、配置和消费者仍按本规范验收；仅借鉴算法/测试方法的来源记录 attribution，不建立虚假源码依赖；没有实际源码消费需求时不 fork Zig 或其他候选。

本轮只维护设计文档，不实施代码、安装工具、创建 fork、clone/fetch/push、修改远端权限或运行构建。完整 FrontendSnapshot、tsfg HIR/Core IR、VM、MLIR/AOT、Language Service 和 SBOM 发布等分别归对应后续阶段。

## 2. 首个来源与工具边界 — Q1 accepted

- 采用 microsoft/TypeScript 的 TypeScript 7.0.2 原生 Go 前端。已核验的上游基线 commit 为 `1e4744d68260a7cb91b62b12edc3f6a2187faaf1`；这是 base 身份，不是尚不存在的本地修改后 fork commit。
- fork 延续既有 xuelongling owner、保留上游 slug/fork network、同级检出及特性分支策略。Integration Manifest 仍锁定实际参与组合的完整 commit OID，不以 tag、branch tip 或 npm 版本替代。
- 该基线的原生模块声明 Go 1.26；必要 Go 工具与依赖纳入 Toolchain Closure，精确补丁版本、可信完整性证据、实际生成/测试依赖及构建选项在实施前锁定核验。当前 R00 锁文件未因此自动改变。
- 不将工程 TypeScript 5.9.2 当作产品前端；不以旧 TS Compiler API 路线冒称 7.0.2 兼容，不等待未来公开 API。源码修改与最小消费边界见第 6 节；具体接口按实际消费者验证，不先建设通用平台。
- Go 服务于编译器侧工具，不进入 Zig 游戏发布运行时。新增来源/工具的设计批准不豁免许可证、完整性、构建及消费验证。
- 该决定的工程边界记录见 [ECP-0003](proposals/0003-native-typescript-source-intake.md)，长期取舍见 [ADR-0013](adr/0013-native-typescript-source-intake.md)。

## 3. 逐文件来源与消费审计 — Q2 accepted

保留完整 fork 历史；由机器展开当前实际参与构建、测试、生成或分发的消费文件清单，每个文件关联来源、上游基线、许可证和消费角色。Intake Ledger 不是只记一条仓库许可证，也不是脱离 Git 历史的 patch queue。

未消费内容明确排除。本地修改和异常许可证由人工可审查的解释补充；普通未修改文件可由一致映射展开，不要求人工重复维护整个上游仓库的每一行。新增实际消费文件未登记即失败，不能依靠宽泛 allowlist 掩盖消费范围增长。

构建工具、编译器 payload 与游戏运行时 payload 的角色不能混淆。生成文件仍须追溯可维护源和生成步骤，构建/测试输入不能因不随产品分发而逃避审计；是否属于 Build Input Set 仍按实际影响 payload 的既有定义判断。

## 4. 保留上游原貌与禁止消费边界 — Q3 accepted

保留上游原目录、版权、许可证及 NOTICE 原始文件，通过明确映射适配检查，不为了满足自研仓规则批量改名、改换行或添加自研版权头。与上游不兼容的检查按仓角色和具体路径调整；危险路径、来源不明、未知许可证仍拒绝，不能整体关闭政策检查。

源码仓可保留未消费的 JS emitter 等上游内容，但不意味着批准 tsfg 暴露产品禁止路径。Q6 对真实耦合作如下明确区分：分析/诊断所需的共享 printer，以及无法无损分离的必要包级源码可以作为编译器构建依赖；产品入口不得使 JS 输入、JS emit 或 JS runtime 回退可达。不能只靠调用者自觉设置 noEmit。

消费清单、实际入口与产物检查及专项负例共同证明禁止路径隔离；不能把尚未核验的不可达代码剔除写成事实。若无法证明隔离，则在 fork 特性分支作必要的最小拆分，不以删除所有共享源码作为先验验收要求，不预先批准另一套 parser 或通过黑盒 CLI 绕过。

现有 R00 policy 与 manifest CI 的“仅两个项目、所有 fork 拒绝”限制需要在后续实施中协调演进成明确准入清单，未批准来源继续失败。实际 LICENSE/NOTICE 文件名映射不能假定所有上游都使用同一字面文件名。文档批准不使现有 gate 自动放行。

## 5. 单来源阶段验收 — Q4 accepted

每个 intake 必须有精确源码/依赖身份、来源许可审计、真实消费者及复跑证据。完成锁定输入预热后，在两个不同的干净 E 盘绝对路径重建实际消费目标，比较声明的可复现输出，沿用现有 Build Identity、输入完整性与适用离线验证要求；不能靠同一增量缓存的两次命中证明重建。

TypeScript 使用真实 `.ts` 正反例，通过源码级消费探针证明 AST、类型及诊断可用，并记录实际源码/工具/选项身份。仅运行版本命令或 npm 预编译产物不足以验收；该探针不是完整 FrontendSnapshot、语言支持声明或 source→MLIR 完成证明。

源码消费目标、确定性结果与副作用边界应在该来源的后续 spec/fixture 中明确。当前批准两路径验收，不新增最低 OS VM、多平台认证或完整 Language Service 前置，也不以裁剪待比较输出掩盖不确定性。

## 6. Fork 直接修改与消费者归属 — Q5 accepted with user clarification

用户明确：在 fork 仓库新建 tsfg 特性分支，直接在该分支修改源码。既有上游代码的必要适配、拆分、接口出口与回归测试都随该 fork 的 Git 历史维护，不另建脱离历史的 patch queue，不复制到产品仓维护第二份上游。

不把“只能新增薄 wrapper、不能改已有上游文件”设为额外限制；仍遵守仅特殊且必需才客制化的既定原则。若需要访问 Go internal，按真实 module/import 边界作最小改动，同级目录不构成绕过规则的依据。

独立于上游的 tsfg 产品实现继续归产品仓；对上游 parser/checker 实施必要语义差异的修改属于 fork 分支，不因它是 tsfg 专用就强行移到仓外。R02a 只证明源码及最小真实消费，完整 FrontendSnapshot、tsfg HIR/Core IR 和具体通信/链接形态由对应消费者阶段完成；不为本轮锁定整个编译器宿主语言或通用桥接设施。

## 7. 生成源码与测试闭包 — Q7 accepted

首次 intake，以及生成器或生成输入发生变化时，必须从锁定输入重演实际消费的生成目标，核对差异并消除未解释差异；经过审查的预期变化保留新旧身份与验证依据。日常 build 可编译已经验真的已提交生成源码，不必每次执行全量生成任务。

生成器、子来源和生成所需依赖同样纳入来源/许可/内容身份与适用离线闭包；不能仅凭 generated 注释、分支名或已有生成结果认定可维护。仅为实际消费目标补齐所需闭包，不要求所有未消费的编辑器、API、打包或发布任务。

必测项目因缺源码、测试数据或工具而 skip 必须计作验收缺失；只有明确排除且有范围依据的项目可以不运行。禁止依赖环境中恰好存在的工具、自动下载工具链或 latest 依赖补齐闭包。具体变量、精确补丁版本和生成目标列表由实施阶段核查，不属于新的产品设计问题。

## 8. 上游升级与回退 — Q8 accepted

从已接纳 fork commit 建独立升级候选分支，合入精确上游 OID，保留已接纳的修改历史；不得重写已被 Integration Manifest 引用的历史。新的本地修改和上游差异均与 Intake Ledger、消费范围及对应测试关联。

每次升级，包括 patch，均比较来源/许可/NOTICE、消费和生成闭包、本地修改、固定语言基线语义/诊断、可复现性及适用性能，不因版本号看似兼容自动准入。差异报告至少能追溯旧/新身份、影响消费者、测试结果、差异解释和准入结论；未执行与不适用分别记录。不具备性能主张的项目不凭空设阈值。

升级未通过时保持现有组合，候选与失败证据按既有规则保留；回退通过新的组合记录指向已验证身份，不移动历史 tag/snapshot。既有语言基线或其他工程承诺需要变化时另行明确决定，不能随源码升级隐式更改。不建设定时自动升级；全面升级运营后置 R13。

## 9. 漏洞与依赖影响记录 — Q9 accepted

按 build-only、编译器 payload、游戏 runtime 的实际角色与可达性判断影响，不能把 build-only 等同于无风险。确认可利用或破坏信任/完整性的问题阻断受影响的新候选；无法判定者保持待核验，不视为无影响，也不以等待判定为理由伪造验收通过。

其余问题记录依据、受影响身份/消费者、负责人、处理期限与复核点。任何风险例外必须由用户明确批准；这不取消既有未知来源/许可证、输入完整性或产品禁止路径的准入门。

当前保留本地依赖清单及其来源、版本/内容身份、消费角色、许可证和影响记录，支撑逐文件审计与后续 SBOM。正式 SBOM 发布、全面安全/升级运营与发布认证归 R13；后置发布不允许丢失当前实际消费依赖。

## 10. 收口与后续交接

本轮设计选择与最终共享理解已获用户确认，grill 已结束，用户已要求综合发布 to-spec。下列事项是后续工作，不是尚未回答的语言/治理设计问题：

- to-spec：把已定范围综合为单来源准入、真实消费与可复现验收的实施规格；不擅自纳入 R02b/IR/AOT 实现。
- 实施前事实核验：精确 Go 补丁/摘要、生成子来源 OID、实际输入和输出清单、平台 profile 映射以及执行身份/权限。这些由 agent 核查；遇到真实冲突才提出最小例外。
- 后续来源：MLIR/LLVM 的具体版本、配置与消费者证据在首次实际使用前准入；已确认的 R03 Core IR 基础设施使用使这项依赖提前，不由已有 LLVM 工具归档推定，也不阻断已具备条件的 TypeScript intake。
- 后续执行授权：本轮不会创建 fork、分支或修改任何代码。进入获授权的实施时先核验实际权限，仅在确实无法自动完成时请用户创建指定 fork 或提供最小必要权限，不索取凭据。

规范收口、Source Intake 验收、真实语言能力和完整 R02a/R01 里程碑状态分别记录，不能相互推定。
